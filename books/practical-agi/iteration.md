# 要素技術③ 反復と検証

## なぜ反復と検証が重要か

長期タスクで一番多い破綻は「**できたつもり**」です。

エージェントがコードを書いて「完了」と報告しても、実際にはコンパイルエラーがあったり、テストが通らなかったりすることがよくあります。

## 検証の3つのレベル

### 1. 構文レベル

- コードがパースできるか
- 設定ファイルが有効か
- 型エラーがないか

### 2. 実行レベル

- テストが通るか
- 実際に動作するか
- エラーが発生しないか

### 3. 意味レベル

- 要求を満たしているか
- 期待した結果が得られるか
- 品質基準を満たすか

## Judge エージェントの役割

Cursor の実験では、各サイクルの終端に **Judge** を配置しました。

Judge の責務：
- 「続行すべきか」を判定
- 品質基準を満たしているか確認
- 次のイテレーションをクリーンに開始

この構造により、調整問題が大きく改善したと報告されています。

## 反復のパターン

### 実行 → 確認 → 修正ループ

```
1. タスクを実行
2. 結果を検証
3. 問題があれば修正
4. 1に戻る
```

シンプルですが、これを**確実に回す仕組み**が必要です。

### クリーンリスタート

長時間稼働すると、エージェントの状態が「ドリフト」（本来の目的からずれる）することがあります。

定期的にクリーンな状態から再開することで、ドリフトを管理できます。

## 「理論上は永遠に続けられるはず」の罠

Anthropic は次のように問題を立てています：

> 「理論上は永遠に続けられるはず」だが、現実には進捗が壊れる

この問題に対処するために、ハーネス（次章で解説）が必要になります。

## まとめ

反復と検証は「やり直す力」です。

一発で正解を出すことを期待せず、**失敗を前提として、検証と修正のループを設計**することが重要です。
