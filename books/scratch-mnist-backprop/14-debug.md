## 完成してもまず動かない

前章までのコードを組み上げて、いざ学習を回した結果がこれです。

![最初の学習結果。損失が下がらずむしろ悪化する](/images/debug_backpropagation/epoch_step1.gif)

1エポック目の損失が 14.5。第10章で見たとおり、何もわかっていない状態でも 2.3 のはずなので、明らかに壊れています。しかもエポックを重ねると悪化していきます。

ニューラルネットワークのバグはたちが悪い。文法エラーと違ってどこも赤くならず、計算は最後まで走り、それらしい数字まで出てきます。ただ賢くならないだけです。この章は、この作品で実際に踏んだバグ2つを、見つけた手順ごと記録したものです。

## 転ばぬ先の _tmp

その前に、作者が仕込んでおいた予防策をひとつ。変数とリストの名前の先頭に `_tmp` と `_tmp_list` を作ってあります。

![変数一覧の先頭に _tmp がある](/images/debug_backpropagation/tmp.png)

Scratch では、変数ブロックを置くと、選択肢の一番上の変数が選ばれた状態になります。

![置いたブロックには一番上の変数が入る](/images/debug_backpropagation/tmp_default.png)

つまり、ブロックを置いたあとで変数を選び直すのを忘れると、その場所には一番上の変数が入ったままになります。一番上をわざと `_tmp` というダミーにしておけば、選び忘れた場所は `_tmp` のまま残るので、あとから探せば見つかります。バグを埋めない工夫ではなく、埋めたバグを見つけられるようにする工夫です。

## バグ1：入力をコピーしていなかった

`_tmp` を頼りに全ブロックを見直すと、さっそくありました。画像を `activations` へコピーするブロックの書き込み先が、`activations` になっていません。

![書き込み先が activations になっていない](/images/debug_backpropagation/debug1.png)

これでは、モデルはずっと真っ白な画像（全部 0）だけを見て学習していたことになります。入力が全部 0 なら、第11章でやったとおり重みの勾配（入力 × デルタ）も全部 0 になって、入力側の重みは1ミリも動きません。

![修正後。activations に書き込む](/images/debug_backpropagation/debug2_.png)

直すと、動いていなかった側の重みが更新されるようになりました。

![修正後、weights の上のほうも動き出した](/images/debug_backpropagation/天才1.gif)

## バグ2：存在しない場所を読んでいた

それでも損失はまだ暴れます。今度は途中の数値を全部画面に出して、順伝播の出口から順に目視しました。すると、ソフトマックスまわりの表示がおかしい。

![確率が9個しかなく、足しても合計と合わない](/images/debug_backpropagation/activations.png)

確率は10個あるはずなのに9個しかない。犯人はこのブロックのどこかです。

![バグが埋まっていた s4_ソフトマックス](/images/debug_backpropagation/softmax2.png)

見つかりますか。最後のループで、`activations` と `s4_exp_vals` という2本のリストを使っています。`activations` は全層共用の長いリストなので、読み書きにオフセットが要ります。ところが `s4_exp_vals` はこのブロック専用の10個だけのリストで、オフセットは不要です。それなのに、exp_vals 側にもオフセットを足した番号でアクセスしていました。11番目、12番目……という存在しない場所を読んでいたのです。

ふつうの言語なら、存在しない場所を読んだ瞬間にエラーで止まって、行番号まで教えてくれます。Scratch は止まりません。空っぽの値が黙って返り、計算は素知らぬ顔で進み、結果だけが壊れます。エラーが出ないことは、Scratch でいちばんきびしい仕様だと思ってください。

![修正後のソフトマックス。exp_vals は素の番号で読む](/images/debug_backpropagation/debug3.png)

直して回すと、今度こそ損失が素直に下がりました。

![修正後の学習。損失が下がっていく](/images/debug_backpropagation/epoch2.gif)

## バグ3：消す係はいたのに、作る係がいなかった

もう1つ。これは、この作品に「続きから学習」（学習フラグ2、第13章）をあとから足したときに踏んだバグです。

症状はこうでした。フラグ2で回すと、1エポック目の平均損失が 27.631。1枚ずつ見ても、600枚ぜんぶがぴったり 27.631 です。

この数字に見覚えがあるはずです。第5章で log の表の先頭に自分で入れた、log(0) の代役です。つまりモデルは600枚全部で「正解の確率は 0 です」と答えている。学習済みの重みから続きを始めたのに、そんなことがあるでしょうか。

種はこうです。旗を押すと、最初に走る「定数初期化」が `activations` を空にします。ゼロから学習（フラグ1）なら、そのあと「重みの初期化」が `activations` を219個の 0 で作り直してくれます。ところが続きから学習は、重みを消したくないので「重みの初期化」を飛ばします。すると `activations` を作り直す係が誰もいなくなる。空のリストの1番目に画像を書き込んでも、Scratch は黙って無視します。順伝播は空のリストを読んで空の答えを出し、正解の確率は 0、損失は保険値の 27.631。エラーは最後まで1つも出ません。

直し方は、フラグ2のときに `activations` と `output_z_arr` だけ作り直す小さなブロックを呼ぶこと。それだけです。

このバグから持って帰れるものが2つあります。1つ、**リストを消す処理を書いたら、作り直す処理がどの道筋でも必ず通るかを確かめること。** 分岐を増やしたときが危ない。2つ、**自分で入れた番兵の値は、事故のときに指紋になること。** 27.631 という半端な数字が画面に出た瞬間、犯行現場が log の表だと特定できました。意味のある定数は、バグの日に恩返しをしてくれます。

## 3つのバグに共通するもの

どのバグも、原因は「リストのどこを指しているか・リストがそこに在るか」の間違いでした。1本のリストにオフセットで相乗りする作り（第4章）は、リストの本数を減らせるかわりに、番号の計算を1か所でも誤るとそこから先の計算が全部壊れます。さらに Scratch はリストが1番目始まりなので、0 から数えるループと混ぜるときに +1 のずれが出やすい。この作品で数字がおかしくなったら、まず疑うのはオフセットとリストの中身です。

:::message
実は、この作品にはもう1つ、無害なバグが残っています。第5章の log ブロックの範囲チェックで、上限を超えたときに書き換える変数が `p_log_input` ではなく `p_exp_input` になっています（exp ブロックからのコピペ痕です）。それでも壊れないのは、log に入ってくる値が確率で、1 を超えることがないからです。この保険の行は一度も実行されません。sb3 を開いて、探して、直してみてください。動作は何も変わりませんが、見つけられたらデバッグの目はもう一人前です。
:::

## デバッグの結論

- 途中の数値を隠さない。リストも変数もステージに出して、目で見る。
- 期待値を先に知っておく。「学習前の損失は 2.3 付近」を知っていたから、14.5 が一目で異常だとわかった。
- ダミーの `_tmp` を選択肢の先頭に置いて、選び忘れを探せるようにする。
- おかしくなったら、まずオフセットと 1始まり/0始まり の混在を疑う。
- 消す処理と作り直す処理をペアで追いかける。分岐を足した日はとくに。

道具は揃い、機械は直りました。最後の章は、この機械で遊ぶ話です。
