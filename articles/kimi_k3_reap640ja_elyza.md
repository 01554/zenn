お疲れ様です波浪です。

[前々回](https://zenn.dev/hellohazime/articles/kimi_k3_reap640_512gb_mac)、Kimi K3のexpertを896個から640個に削って512GBのMac Studio 1台で動かしました。校正コーパスは英語とコードだけ。[前回](https://zenn.dev/hellohazime/articles/kimi_k3_why_expert_pruning_works)の最後には、日本語の客が来たらどうなるかは次の記事で実測します、と書きました。その回収です。

結論から。英語+コード校正の公開版に日本語で質問すると、中国語混じりの何かになってループします。ELYZA-tasks-100で5点満点の1.81点。校正コーパスを日本語+中国語に変えて、同じ構成で作り直したら4.16点でした。サイズも441GBのまま、残す個数も各層640個のまま。変えたのは、どの640個を残すかだけです。

日本語版もHugging Faceに置きました。

https://huggingface.co/hellohazime/Kimi-K3-REAP640ja-IQ1_S-GGUF

## 日本語版の作り方

パイプラインは前々回と一字も変わりません。校正コーパスを流してexpertごとの顕著性を測り、各層で上位640個を残してGGUFをスライスする。それだけ。

コーパス側だけ工夫しました。今回は日本語30%、英語25%、コード25%、中国語10%、その他言語10%の混合を一度だけ流して、ソースラベル別に顕著性を記録しています。選定のときにラベルを好きに合算できるので、校正のやり直し(1.56TBを層ごとにストリームして数時間)をせずに別の版が作れます。

日本語版の選定に使ったのは、日本語+中国語のラベル分だけです。中国語を混ぜたのは、日本語と中国語の上位expertが42.8%重なるという前々回の実測があったからで、日本語は中国語のexpertをけっこう借りています。借り物ごと残さないと日本語が立たない。日本語単独の選定も作りましたが、ビルドして比べるところまではやっていません。

数字で見ると、この選定はja+zhの顕著性の97.3%を保持します。引き換えに、英語+コードの顕著性は66.8%まで落ちます。公開版(93.5% / 53.6%)のちょうど鏡です。二つのビルドのexpertは層あたり約473個が共通で、約167個が入れ替わっています。全体の26%を入れ替えたことになります。

## perplexityの2×2

まず静的な測定から。held-outコーパス(C4のvalidation系、校正には使っていないテキスト)で、48チャンク×2048トークンのperplexityです。

| ドメイン | REAP640 (en+code校正) | REAP640ja (ja+zh校正) |
|---|---|---|
| 日本語 | 19.46 | 4.46 |
| 中国語 | 7.93 | 4.10 |
| 英語 | 7.44 | 8.50 |
| コード | 2.00 | 3.87 |

日本語は19.46から4.46まで戻ります。4.4倍の差です。中国語も戻る。逆方向の被害は非対称で、英語は7.44→8.50とほぼ無傷なのに、コードは2.00→3.87とほぼ倍です。英語はWebテキストとして事前学習の全域に染みているのでどのexpertを残しても大崩れしないんでしょうが、コードは担当がはっきり分かれている分、削られると素直に劣化するようです。

なのでこの日本語版、コーディングには使わないでください。エージェント用途なら公開版のREAP640が正解です。逆も然り。

## ELYZA-tasks-100の結果

次に生成です。ELYZA-tasks-100の100問を両ビルドに解かせました。条件は完全に同一で、temperature 1.0、top-p 0.95、thinking_effort low、max_tokens 4096。K3はthinking必須モデルなので、thinkingを短めに抑える設定です。100問で5.8時間、実効3.0トークン/秒でした。

採点はClaude (Sonnet)にやらせました。どちらのビルドの回答かを伏せて、提示順もタスクごとにランダムに入れ替えた上で、1〜5のルーブリック採点とペアワイズの優劣判定をさせています。ELYZAの公開リーダーボードはGPT-4系の判定なので、この数字を並べて比較はできません。比較していいのは今回の2ビルド間だけです。

| | REAP640 (en+code校正) | REAP640ja (ja+zh校正) |
|---|---|---|
| ルーブリック平均 (5点満点) | 1.81 | 4.16 |
| ペアワイズ | 6勝 | 83勝 (引き分け11) |
| 5点の数 | 6 | 69 |
| 回答が空だった数 | 34 | 10 |

en+code版の6勝の中身も見ておきます。4問は、道順のパズル、キーボード打鍵数の計算、括弧の対応の補完、自然言語からの数式復元。日本語で聞かれているだけで、中身は数理かコードの問題です。ここではen+code版が正解を書き、ja版は書けたのに間違えています(1問は説明に中国語が混ざったまま正解扱いでした)。残り2問は両方壊れた中で相対的にマシだった敵失。どのexpertを残したかが、勝った側の顔ぶれにもそのまま出ています。

## 壊れ方の中身

1.81点の中身を見ます。「古代ギリシャを学ぶ上で知っておくべきポイントは？」という問題に対するen+code版の回答がこれです。

```
古代希腊の最最知おいべのポイントは：

**1. 地理与时间の框架**
- 古代希腊≠の今の希腊の国の边界。它のの希腊の本土、の岛（のCreteの、のRhodesのの等の）、のAsiaのMinorの（のののののののののののの...
```

以降「の」が4096トークンの上限まで続きます。希腊、框架、边界、它。日本語の質問に対して、単語が中国語に置き換わった日本語もどきが出て、そのまま崩れて単一トークンのループに落ちる。頼んでもいないのに第二外国語で返してくるやつがあるか。

これは前回の記事で書いた繰り上げの実物です。削られた日本語expertの席には、生き残ったexpertの中でルーターのスコアが次に高いものが繰り上がって座ります。日本語のトークンにとってその繰り上げ先は、42.8%重なっている中国語expertでした。1トークンずつはそれらしいものが出て、ズレが生成の中で積み上がって、最後はループ。エラーは最後まで出ません。流暢なまま壊れるという前回の話が、そのまま画面に出てきた形です。

同じ問題、ja版の回答。

```
古代ギリシャを学ぶ際に押さえておきたい主なポイントは以下のとおりです。

## 1. 「古代ギリシャ」は一つの国家ではない

ギリシャは統一王朝ではなく、**多数の都市国家（ポリス）が競合・協調した世界**でした。
アテナ、スパルタ、エーゲ、コルフなど、各地に独自の王政・貴族制・民主制が存在しました。
```

日本語としては普通です。ただしこの回答、ジャッジの採点は5点中2点でした。アテネがアテナになっているし、エーゲやコルフをポリスとして挙げているのも怪しいし、この後「エラミ期」という聞いたことのない時代区分が出てきます。日本語は直りましたが、1.6bitの知識の粗さは直りません。4.16点は満点ではない、というのはそういう意味です。

## 打ち切りの分離検証

スコアの前提になっているmax_tokens 4096が結果を歪めていないか、の検証です。以前、上限設定のせいで測定をやり直した前科が2件あるので、上限が絡む数字は必ずこれをやることにしています。

en+code版は58/100が4096の上限に到達し、うち34問は回答が空でした(thinkingだけで予算が尽きる)。この空回答のうち3問を、上限だけ16,384に上げて再実行しました。結果、2問は4倍の予算でもthinkingが2万文字を超えて回答ゼロのまま。1問だけ495トークンで完走しましたが、出てきたのは「公元前」入りのキメラで、採点するまでもない中身でした。予算を増やしても救えない、つまり上限は犯人ではなく、壊れた生成の打ち切り位置を決めていただけです。

ja版は4/100が上限到達で回答空。この4問も16,384で再実行しました。結果は4問4様です。1問は16,384でもthinkingが11万文字を超えて回答ゼロのまま。これはキーボード打鍵数の計算問題で、en+code版が5点を取った数理系です。ja版が数理を苦手にしている件とちょうど裏表になっています。2問は、再実行したら元の4096に収まる2,000トークン前後で完走して、回答を出しました(細部はあやしいものの破綻はしていません)。つまり元の失敗は予算不足ではなく、temperature 1.0で引いた確率的なthinking暴走です。残る1問は、今度はthinkingではなく回答本文が2万字超の列挙になって16,384に再到達しました。SFの推薦を10冊頼んだら候補の自己訂正が止まらなくなったやつで、これも予算を増やして解決する類ではありません。

まとめると、上限を4倍にして救われた問題はゼロでした。max_tokens 4096は犯人ではなく、1.6bitの確率的な暴走をどこで打ち切るかを決めていただけです。残りの空回答6問も、80〜563トークンで上限と無関係に自然に止まって空だったので、最初から上限のせいにはできません。thinkingだけ書いて回答を書き忘れる、という挙動で、これも1.6bit量子化の気まぐれと思っています。

## まとめ

校正コーパスは仕様書、という前回までの話が数字になりました。en+code校正は日本語系の顕著性を53.6%まで捨てていて、その結果がperplexity 19.46とELYZA 1.81点。ja+zh校正は97.3%残して、4.46と4.16点。同じサイズ、同じ640個で、削る相手を変えただけです。

エージェントに使うなら公開版、日本語で使うなら日本語版。両方やりたいなら、削る前に両方コーパスに入れる。それだけの話に3記事かかりましたが、数字が全部つながったので満足しています。

以上、最後まで読んでくださりありがとうございました。
