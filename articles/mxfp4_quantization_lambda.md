お疲れ様です波浪です。

あるモデルの量子化をしています。8層の MoE（expert 128個・top-4）で、BF16 で 2.8GB。LLM と比べれば小さいので、GPU なしで動くじゃろ、と AWS Lambda に載せて動かしていました。

実際、動きます。動くんですが、それなりに料金がかかる。1件あたり ¥0.034 です。月に何十万件も流すと効いてきます。

じゃあ量子化して安くできないかな、と思ったのが始まりです。

## いろいろ削ってみた

とりあえず作れるものを一通り作りました。

| 版 | モデルサイズ | 元との比 | 実行時の常駐メモリ |
|---|---:|---:|---:|
| 元(BF16) | 2.80GB | 100% | 4.58GB |
| INT8(8bit) | 1.55GB | 55% | 2.25GB |
| 混合(重要な expert=8bit / 残り=2bit) | 1.40GB | 50% | 2.12GB |
| 4bit(MXFP4) | 0.95GB | 34% | 1.67GB |
| 2bit | 0.61GB | 22% | 1.33GB |

きれいに減りました。2bit まで行くと元の 1/5 です。

サイズが減ったので当然速くなって安くなるだろう、と思って測ったら、そうはなりませんでした。

## 速度と料金を測ると INT8 が一番よかった

| 版 | メモリ設定 | 1件あたりの処理時間(warm) | 1件あたりの料金 |
|---|---:|---:|---:|
| 元(BF16) | 7168MB | 2.0 秒 | ¥0.034 |
| INT8 | 6144MB | 1.2 秒 | ¥0.018 |
| 4bit(MXFP4) | 6144MB | 2.7 秒 | ¥0.041 |

**4bit が一番高い。** 元より高い。

Lambda の料金は「メモリ設定 × 実行時間」で決まります。そしてメモリ設定は CPU の割り当てと紐づいていて、メモリを小さくすると CPU も減ります。だから「モデルが小さくなったからメモリ設定を下げよう」とすると、その分 CPU が減って処理時間が伸び、結局トータルでは安くならない、ということが起きます。

MXFP4 の 0.95GB は 2048MB のメモリ設定にも載る大きさですが、そこまで下げると CPU が足りず、処理時間の伸びのほうが勝ちます（この点は実測中で、数字が出たら追記します）。

で、そもそも 4bit は **同じメモリ設定でも BF16 より遅い**。ここが不思議でした。データ量は 1/3 なのに。

今日はここを掘ります。

## BF16 の 16bit を、4bit にどう押し込むか

今回採用しているのは MXFP4 です。名前は聞いたことがあったものの中身をよく知らなかったので、確認していきました。

まず、対象のモデルの expert 重みの分布を実測すると、こうなっていました。

| 範囲 | 実測値 |
|---|---|
| 全重みの最小〜最大 | −0.90 〜 +1.09 |
| 半分(50%)が収まる範囲 | ±0.031 |
| 99% が収まる範囲 | ±0.18 |

BF16 が表せるのは 10 の 38乗くらいの範囲です。それに対して、実際の重みは **99% が ±0.18 に収まっている**。

±0.18 で収まる重みってなんやねんそれ、という話です。BF16 の広大な表現範囲は、この用途ではほぼ空き家になっている。

MXFP4 はここに目をつけます。

## 指数を「1個ずつ」から「32個で1個」へ

BF16 は、数値1個ごとに「符号1bit + 指数8bit + 仮数7bit」を専有します。この指数8bitが 10^38 の広さを担当している部分です。

MXFP4 はこうします。

- **指数8bitは32個で共有**
- 各数値は **符号1bit + ラベル3bit の合計4bit** だけ

32個の重みを1ブロックとして扱い、ブロックごとに倍率（＝共有する指数）を1個持ちます。

実際のモデルの1ブロック目を、手で追ってみます。

### 1. 32個の重みを取り出す

先頭から32個。実測値の一部を挙げるとこうです。

```
w0  =  0.013916
w1  =  0.017700
 ...
w30 = -0.029907
w31 = -0.006989
```

### 2. 絶対値の最大を見る

このブロックでは **0.107422** でした。

### 3. 最大値が 6 になるように割る

なぜ 6 かというと、後で出てくる 4bit の表で表せる最大値が 6 だからです。ブロック内の最大値をその 6 に合わせにいきます。

```
0.107422 ÷ 6 = 0.017904
```

### 4. 2の冪のうち、切り上げ側を選ぶ

倍率は 2 の冪しか使えません。0.017904 の近くにあるのは、

```
1/32 = 0.03125
1/64 = 0.015625
```

数としては 1/64 のほうが近いです。でも **1/64 を選んではいけません**。

1/64 で割ると `0.107422 ÷ 0.015625 = 6.875` になり、表で表せる最大の 6 を超えてしまいます。はみ出した分は 6 に丸められる（クリップされる）ので、ブロック内で一番大きい重みが一番壊れることになります。

実際に 1/64 で計算してみると、このブロックの最大誤差は **0.013672** まで悪化しました。1/32 なら後述のとおり 0.006989 です。倍近く違う。

なので**切り上げ側の 1/32 を採る**。値域からはみ出さないことを優先する、という設計です。

### 5. 倍率をブロックの倍率として保存する

この 1/32 を、32個ぶんの共有倍率として 8bit で保存します。E8M0 という形式で、指数だけを持ち仮数を持ちません。値は必ず 2 の冪になります。

実際の量子化済みファイルを読むと、このブロックの倍率バイトは **122** でした。

```
2^(122 - 127) = 2^-5 = 0.03125 = 1/32
```

手で求めた値と一致します。

### 6. 32個の重みを倍率で割る

| | BF16の実値 | ÷ 0.03125 |
|---|---:|---:|
| w0 | 0.013916 | 0.445 |
| w1 | 0.017700 | 0.566 |
| w30 | −0.029907 | −0.957 |
| w31 | −0.006989 | −0.224 |

### 7. 4bit で表せる値に丸める

4bit の内訳は **符号1bit + ラベル3bit** です。ラベルと値の対応は固定の表で決まっています。

| ラベル | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| 値 | 0 | 0.5 | 1 | 1.5 | 2 | 3 | 4 | 6 |

内部的には 4bit をさらに分割したミニ指数と仮数、という構造になっているらしいのですが、そこまで見ると面倒です。**8種類の値に番号を振った表**だと思って差し支えありません。符号ビットと合わせて、−6 から +6 までの15種類（0 は符号違いで重複）を 4bit で表します。

先ほど割った値を、この表の一番近いところに丸めます。

| | ÷ 0.03125 | 丸め先 | 4bit |
|---|---:|---:|---|
| w0 | 0.445 | 0.5 | `0001` |
| w1 | 0.566 | 0.5 | `0001` |
| w30 | −0.957 | −1.0 | `1010` |
| w31 | −0.224 | 0 | `1000` |

`1010` は「符号1 + ラベル2(=1.0)」で −1.0、`1000` は「符号1 + ラベル0(=0)」で −0 です。

### 8. 保存

この 4bit を繋げていくことでモデルサイズを減らしています。1バイトに2個詰まります。

```
00010001 | ..... | 10001010
```

実際のファイルを読むと、先頭バイトは `00010001`、末尾バイトは `10001010` でした。手で追った結果と一致します（1バイト内では下位ニブルが先の重み）。

倍率は別の配列に保存されていて、こちらは `01111010`（=122）です。

### 9. 計算時：BF16 に戻す

計算するときは、カーネルが浮動小数点数を要求するので、全部 BF16 に戻します。

まずバイトを2つのニブルに割ります。

```
00010001 → 0001 | 0001
```

この時点ではまだラベルです。表を引いて値にします。

```
0.5, 0.5, ... , -1.0, -0.0
```

そこにブロックの倍率を掛け戻します。

```
0.5 × 1/32 = 0.015625
0.5 × 1/32 = 0.015625
...
-1.0 × 1/32 = -0.031250
-0.0 × 1/32 = -0.000000
```

元の BF16 はこうでした。

| | 元(BF16) | 復元後 | 誤差 |
|---|---:|---:|---:|
| w0 | 0.013916 | 0.015625 | +0.001709 |
| w1 | 0.017700 | 0.015625 | −0.002075 |
| w30 | −0.029907 | −0.031250 | −0.001343 |
| w31 | −0.006989 | −0.000000 | **+0.006989** |

このブロック32個での最大誤差は **0.006989**、平均誤差は 0.003718、相対RMS誤差は **14.9%** でした。

一番ずれたのは w31 です。元が −0.006989 だったのが、まるごと 0 になりました。倍率 1/32 での1目盛りは 0.5 × 1/32 = 0.015625 で、−0.006989 はその半分に届かないので 0 に落ちます。**ブロックの中で小さい重みほど、まるごと消える**。これが 4bit 量子化の代償です。

ブロック内のラベル分布を見ると、32個中 9個が 0 に落ちていました。約3割です。

## で、なぜ遅いのか

ここまで追うと、遅い理由が見えてきます。

計算の直前に、**毎回この復元作業が入る**からです。

1. バイトをニブルに割る
2. ラベルから値を引く
3. ブロックの倍率を掛ける
4. できた BF16 で行列積を回す

BF16 のままなら 4 だけです。1〜3 が丸ごと追加されます。しかも現代の CPU は積和演算に専用命令を持っていて、そこは元から速い。速いところは変わらず、前処理だけが増える。

データ量が 1/3 になったことが効くのは、メモリ帯域がボトルネックになっている場合です。ところが expert 1個ぶんの重みは 2.5MB 程度で、キャッシュに載ってしまう。載ってしまえば帯域は効かず、追加された前処理のコストだけが残ります。

INT8 が一番よかったのも同じ理屈で説明がつきます。INT8 は倍率が出力チャネル単位で1個あればよく、ニブル分割も不要で、1バイトから素直に復元できる。復元コストが 4bit よりずっと軽い。そのうえサイズは半分近くまで減るので、メモリ設定を1段下げられて、そのぶん安くなります。

## まとめ

- 重みの実測分布は驚くほど狭く（99% が ±0.18）、BF16 の広い表現範囲はほぼ使われていない
- MXFP4 は指数を32個で共有し、各値は「符号1bit + 8種類の表のラベル3bit」にする
- ブロックの倍率は 2 の冪で、**切り上げ側**を選ぶ。切り下げるとブロック最大の重みがクリップされて壊れる
- サイズは確実に減る。BF16 2.80GB → 4bit 0.95GB（34%）
- ただし計算前に毎回復元が要るので、**キャッシュに載る規模のモデルでは 4bit は遅い**
- 少なくとも今回の条件（AWS Lambda・CPU 実行・8層 MoE）では、料金まで含めると INT8 が最良だった

「小さい = 速い」ではない、というのが今回の結論です。4bit が輝くのは、モデルが大きくてメモリ帯域が本当にボトルネックになっている場合や、そもそも 4bit を直接計算できるハードウェア（FP4 対応のテンソルコアなど）がある場合で、CPU 上の小さめのモデルではそうならない。

配布サイズが効く場面（ブラウザに載せるとか）では 4bit の 0.95GB は魅力なので、用途で使い分けるのが正解っぽいです。
